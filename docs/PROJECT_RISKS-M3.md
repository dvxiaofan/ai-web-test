# 项目问题与风险分析

> 分析时间：2026-07-24
>
> 本文基于当前仓库的静态代码、测试、配置和项目文档分析。文中将“已确认事实”“潜在风险”和“待验证项”分开描述，避免把产品能力缺口误判为已经发生的代码故障。

## 1. 结论摘要

当前项目已经形成了较完整的测试编排基础：源码发现、浏览器探索、测试计划、人工审批、Playwright 执行、风险拦截和报告生成均有对应实现。

当前最主要的问题不是已经发现了某个确定的高危漏洞，而是项目仍处于 alpha 阶段，以下能力尚未达到可直接用于生产级、无人值守业务回归的程度：

- 依赖安装还不可完全复现；
- 浏览器 E2E 在 CI 中不是强制执行；
- 认证和测试数据生命周期需要项目方自行提供；
- AI 提案还不能直接可靠地进入可执行测试流程；
- 自动生成的 smoke 场景主要验证可达性和页面渲染，不等于业务规则覆盖；
- 变更、删除、支付、发布等有状态流程仍需要严格的人工和环境控制。

## 2. 已确认的项目事实

### 2.1 依赖环境不可完全复现

**结论：已确认。**

仓库当前没有 `package-lock.json`。项目文档也明确要求在正式使用前生成并提交 lockfile。当前环境同时没有安装 `node_modules`，因此本次分析没有执行构建和测试。

**影响：**

- 不同开发机或 CI 环境可能解析到不同的依赖版本；
- 不能直接使用 `npm ci` 保证严格一致的安装结果；
- 当前仓库状态不能据此确认构建和测试全部通过。

**依据：**

- `package.json`
- `docs/READINESS.md`
- `docs/CI.md`

**建议：**

1. 执行 `npm install` 生成 `package-lock.json`；
2. 将 lockfile 提交到仓库；
3. CI 改用 `npm ci`；
4. 固定 Playwright 浏览器版本和安装步骤。

### 2.2 浏览器 E2E 不是默认强制验证

**结论：已确认。**

`tests/e2e/sample-app.test.ts` 使用 `describe.skipIf(!runE2E)`，只有环境变量 `AI_WEB_TEST_E2E=1` 时才执行样例应用的完整浏览器链路。

**影响：**

- 默认测试结果主要覆盖单元和集成逻辑；
- CLI、真实浏览器、目标进程和浏览器策略之间的集成回归可能不会被持续发现；
- Playwright 浏览器缺失、启动失败、页面行为变化等问题可能延迟到实际使用时才暴露。

**依据：**

- `tests/e2e/sample-app.test.ts`
- `docs/IMPLEMENTATION_PLAN.md`

**建议：**

- 在 CI 中安装 Chromium；
- 至少为受控 fixture 强制执行一次 E2E；
- 将单元/集成测试和浏览器 E2E 分成明确的 CI 阶段；
- 对不允许启动本地监听器的环境保留独立的非 E2E 流程。

### 2.3 认证自动化尚未完成

**结论：已确认。**

配置中虽然存在 `usernameEnv`、`passwordEnv` 和 `setupScenarioId`，但文档明确说明这些字段目前只是预留配置。执行器实际依赖预先生成的 Playwright `storageState`。

**影响：**

- 工具不能自动完成登录、刷新认证状态或创建登录态；
- 新项目接入时，需要额外编写账号准备流程；
- 登录态过期、权限变化和多角色账号管理需要项目方自行维护。

**依据：**

- `src/core/config.ts`
- `src/cli.ts` 中的 `buildStorageStateMap`
- `src/execution/executor.ts` 中的角色执行逻辑
- `docs/CONFIGURATION.md`
- `docs/READINESS.md`

**建议：**

- 优先支持显式的 Playwright auth setup 场景；
- 保存 storage state 前增加过期和目标环境校验；
- 对缺失或失效的 storage state 输出单独的认证失败分类；
- 不要将账号密码值写入配置或 artifact。

### 2.4 测试数据清理和回滚契约尚未完成

**结论：已确认。**

项目能够要求变更场景配置测试数据命名空间，也能限制风险等级，但没有通用的数据创建、清理、回滚和失败恢复机制。项目文档把这些内容列为 release gate。

**影响：**

- 变更类测试可能留下脏数据；
- 测试失败后可能无法自动恢复环境；
- 多次执行可能互相污染，导致结果不稳定；
- 如果误连共享环境，影响会超出测试工具本身。

**依据：**

- `src/core/policy.ts`
- `src/planning/approval.ts`
- `docs/SECURITY.md`
- `docs/READINESS.md`
- `docs/IMPLEMENTATION_PLAN.md`

**建议：**

- 为每个变更场景定义 setup、execute、cleanup 三段生命周期；
- 强制要求唯一且可追踪的 test-data namespace；
- 将清理失败作为独立的高优先级结果；
- 破坏性流程使用单独配置、单独环境和单独审批。

### 2.5 AI 场景提案尚未闭环到可执行测试

**结论：已确认。**

当前 AI 能力主要用于场景建议和失败归因。AI 输出会被脱敏、限制上下文大小并做结构校验，但还没有完成“提案审核后导入可执行场景”的完整产品流程。

**影响：**

- AI 不能替代人工编写和审查业务场景；
- 不能把 AI 输出直接当作已验证的业务覆盖；
- AI 的语义判断仍可能不准确，尤其是权限、数据状态和业务规则判断。

**依据：**

- `src/ai/provider.ts`
- `src/ai/scenario-planner.ts`
- `src/ai/triage.ts`
- `docs/READINESS.md`
- `docs/IMPLEMENTATION_PLAN.md`

**建议：**

- 保持 AI 输出为 advisory 状态；
- 增加人工审核后的导入动作；
- 导入前重新执行场景 schema、风险、host 和 locator 校验；
- 将 AI 推断与确定性运行证据明确区分。

### 2.6 自动生成的 smoke 场景不代表业务回归覆盖

**结论：已确认。**

`generateRouteSmokeScenarios` 生成的默认场景主要包含导航、URL 断言、页面 body 可见性断言以及可选截图。它不会自动覆盖表单提交、数据创建、权限边界或复杂业务规则。

**影响：**

- 路由数量较高不代表业务测试覆盖率高；
- 页面能打开不代表 API、数据、权限和业务流程正确；
- 动态路由默认可能被跳过；
- 需要用户维护业务场景目录。

**依据：**

- `src/scenarios/generator.ts`
- `src/scenarios/io.ts`
- `docs/SCENARIOS.md`

**建议：**

- 把 route smoke 和业务场景分开统计；
- 报告中分别展示可达性覆盖、接口断言覆盖和业务场景覆盖；
- 为关键业务模块补充用户维护的场景 JSON；
- 对动态路由提供参数 fixture 或显式测试数据。

## 3. 潜在风险：目前没有证据证明已经发生

以下内容是基于实现方式推断出的使用风险，不代表仓库中已经确认存在对应故障。

### 3.1 静态发现可能存在漏报和误报

项目使用通用源码分析并提供若干框架识别能力，但任意 Web 项目的路由、API、权限和业务模块写法都可能超出当前 extractor 的识别范围。

**需要验证：**

- 使用 React、Vue、Next、Nuxt 以外的项目验证路由发现；
- 使用动态拼接 URL、二次封装 HTTP client 和代码生成 API 验证 API 发现；
- 对比源码真实路由清单和 inventory 清单。

### 3.2 主机策略和真实网络行为需要实测验证

代码已经实现 host allowlist、请求方法风险判断和 WebSocket fail-closed，但复杂场景仍需要真实浏览器验证，例如：

- 重定向到外部 origin；
- iframe、弹窗和新页面；
- service worker、WebSocket 和第三方资源；
- 不同端口、协议和 wildcard host 配置。

**结论：**当前只能确认存在防护代码，不能仅通过静态阅读证明所有浏览器网络路径都不会绕过策略。

### 3.3 视觉快照是确定性差异检测，不是语义视觉判断

当前视觉能力主要比较截图内容的 digest。它可以发现截图发生变化，但不能判断变化是否符合设计预期，也不能自动理解布局、颜色或交互语义是否正确。

**需要验证：**

- 动态时间、随机 ID、广告和异步数据是否造成误报；
- 不同浏览器、字体和操作系统下的稳定性；
- baseline 更新流程是否经过人工审查。

### 3.4 Artifact 可能包含敏感业务信息

截图、Trace、Console、URL 和页面错误信息可能包含账号、业务数据或内部路径。代码提供了脱敏和显式持久化开关，但最终存储位置、访问权限、保留周期和备份策略仍由使用方负责。

**建议：**将 artifact 目录视为敏感数据，限制访问权限并配置保留周期；生产环境不要默认开启截图和 Trace。

## 4. 当前未确认的事项

以下事项本次没有足够运行证据，不能下确定结论：

- 当前版本是否可以在本机完整通过 `npm run build`；
- 当前版本是否可以完整通过 `npm run typecheck` 和 `npm test`；
- Playwright Chromium 是否可以正常启动；
- 复杂重定向、WebSocket、弹窗和多页面行为是否全部符合策略预期；
- 在真实目标项目上的路由、API 和模块发现准确率；
- 多角色 storage state、视觉 baseline 和 artifact retention 在长期运行中的稳定性。

## 5. 优先级建议

### P0：发布和验证基础

1. 生成并提交 `package-lock.json`；
2. 在 CI 中执行 build、typecheck、unit/integration tests；
3. 在受控 fixture 上强制执行 Chromium E2E；
4. 固定 Node、npm、Playwright 和浏览器版本。

### P1：真实项目接入能力

1. 完成认证 setup 和 storage state 生命周期；
2. 完成测试数据 namespace、cleanup 和 rollback 契约；
3. 增加关键业务场景的人工维护模板；
4. 将 smoke coverage 与 business coverage 分开报告。

### P2：AI 和扩展能力

1. 增加 AI 场景提案的人工审核和导入流程；
2. 扩展框架和 API extractor；
3. 增加真实项目样本进行发现准确率对比；
4. 完善 artifact 脱敏、保留和访问控制策略。

## 6. 总体判断

当前没有根据静态分析确认的高危安全漏洞可以直接下结论。更准确的判断是：项目的安全闸门和核心架构已经具备，但仍存在若干已明确记录的产品能力缺口和发布成熟度风险。它适合作为受控环境中的测试发现、计划审批和只读冒烟测试基础设施，暂不应被当作可以直接连接生产或无人值守执行高风险业务流程的完整测试平台。
